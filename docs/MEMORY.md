## Architecture Decisions

| Decision | Reason |
|---|---|
| On-demand slot generation (no pre-stored slots) | Avoids DB bloat; computed at query time via `appointments/utils/intervals.py` |
| UUID7 primary keys on all models | Better DB performance + sortable by time |
| Bruno collection scope (2026-08-27) | Bruno is not an automatic project or PR acceptance requirement. API-client requests belong in a separately scoped automation task generated from implemented URLs and ePRDs unless the user explicitly requests them with the feature. |
| Center-scoped data isolation via `X-Center-ID` header | Multi-tenant design requirement |
| Customer associate list center precedence (2026-08-19) | `CustomerAssociateListView` keeps both optional `X-Center-ID` and `center_id` query filtering. When the header is present it is the exclusive center filter; query center IDs are used only when the header is absent. |
| Customer associate list role join (2026-08-19) | The list filters the intermediate associate-center assignment against each returned customer-assignment center before selecting its role. The response retains the existing nested `role` field and avoids multi-center join fan-out. |
| Associate persisted center count (2026-08-20) | `Associate.centers_count` counts all existing `AssociateCenterAssignment` rows regardless of active state. Runtime assignment mutations refresh one associate through a correlated subquery update; center deletion bulk-updates affected associates before the cascade while excluding that center; `update_associate_centers` independently updates all associates. |
| Associate list/create frontend contract (2026-08-24) | Admin-only `GET`/`POST /associates/` uses a maximum-three center preview without assignment flags. | `uv` as sole package manager | Faster, reproducible, replaces pip entirely |
| All docs in `docs/` folder | Enforced by `CODING_RULES.md` |

## Conventions Established Through Collaboration

**Naming Standards (2026-05-11)**
- **NO abbreviations** in code: variables, parameters, loop variables, annotations
- Use explicit, brief, formal names
- Examples: `count` not `cnt`, `assignment` not `asg`, `service` not `s`
- Added to CODING_RULES.md Section 1 w/ examples
- Why: Readability, consistency, prevents ambiguity (especially in subquery annotations)

**Django FK Access (updated 2026-08-27)**
- Use `relation.pk` when the related model instance is already available.
- Direct `<field>_id` assignment is permitted specifically while constructing objects for `bulk_create()`; do not hydrate related objects solely to satisfy style.
- This exception does not apply to ordinary single-object assignments or queryset filters.
- In `bulk_create()` paths, prefer `center_id=<validated_uuid>` over per-row `Center` lookups or unnecessary batch hydration.
- `docs/CODING_RULES.md` still contains an older unconditional prohibition and should be reconciled in a separately authorized documentation change.

**ORM Single-Object Lookups (2026-07-27)**
- Use `filter(...).first()` for serializer + utility object lookups.
- Don't introduce direct `.get()` lookups; explicitly handle missing result where required.

**Serializer Add/Remove Actions (2026-08-04)**
- Keep `add_*`/`remove_*` relation handling simple: accept write-only `{id}` lists, pop each list from `validated_data` w/ empty-list fallback, delegate each op to small action helper.
- Each action helper returns immediately for empty input, validates supplied IDs against allowed parent scope w/ one ORM query + set difference, raises error on its own serializer field, then calls related manager's bulk `add()`/`remove()` w/ validated IDs.
- Keep `create()`/`update()` as transaction-level orchestration: save main instance, run remove before add so add wins for IDs present in both inputs, update maintained counts, refresh only required fields, rebuild any response preview, return instance.
- Avoid duplicating relation-ID normalization/validation in `create()`/`update()`; don't add prevalidation structures when action helpers can perform complete operation directly.

**View Querysets (2026-07-27)**
- Keep reusable endpoint queryset construction in a `*ViewMeta` mixin derived from `BaseGenericAPIView`.
- Concrete views should subclass the mixin and call the queryset method through `self`, following `CenterViewMeta`; do not create standalone queryset utility functions for this pattern.
- Use the established `filter_kwargs = {}` pattern for request/user-specific queryset scoping; do not introduce custom permission-queryset mixins.
- Do not add `http_method_names`; rely on the project’s established base view classes.
- Keep a strict serializer/view queryset boundary: serializers must never import or reuse queryset builders from views or `*ViewMeta` classes. Serializers resolve their own required models directly through model managers.
- Serializer imports from `utils/db.py` should be limited to state-changing utilities such as count refreshes, increments, decrements, cancellations, and related mutation helpers; object/queryset resolution belongs directly in the serializer, while optimized response querysets belong exclusively in `*ViewMeta`.
- Serializer representation methods must consume prefetched `to_attr` data supplied by the view queryset and must not query related models or managers per serialized object.

**Serializer and Route Ownership (2026-08-10)**
- Serializer `create()` and `update()` methods own persistence. Views may resolve route context and pass it to `serializer.save(...)`, but must not capture or use its return value, assign `serializer.instance`, or reload a saved object for write-response serialization.
- Route-bound object getters accept no identifier arguments and resolve the required `self.kwargs["pk"]` with `get_object_or_404`. A `*ViewMeta` may be shared only by views whose `pk` identifies the same resource type.
- Resource URLs use one canonical `<uuid:pk>`. Service documents are deleted through `/programs/program-result-documents/<uuid:pk>/`; the parent result is obtained from the resolved document instance.
